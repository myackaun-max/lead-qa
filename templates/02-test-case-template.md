# Шаблон тест-кейсу

## Формат ID
`TC-[МОДУЛЬ]-[NNN]`, напр. `TC-AUTH-001`. Для API: `TC-API-[РЕСУРС]-[NNN]`.

## Пріоритет
| Пріоритет | Коли |
|---|---|
| P1 | Критичний шлях, гроші, дані, безпека. Входить у smoke |
| P2 | Основна функціональність. Входить у регресію |
| P3 | Другорядні сценарії, граничні значення |
| P4 | Косметика, рідкісні випадки |

## Таблиця кейсів
| ID | Назва | Передумови | Кроки | Дані | Очікуваний результат | Пріоритет | Тип | Ризик | Автоматизувати |
|---|---|---|---|---|---|---|---|---|---|
| TC-AUTH-001 | Вхід з валідними обліковими даними | Користувач зареєстрований і активний | 1. Відкрити /login 2. Ввести email і пароль 3. Натиснути «Увійти» | email: qa.user@example.com, пароль: Valid#123 | Перехід на головну, показано ім'я користувача, видано сесію (cookie HttpOnly, Secure) | P1 | Функціональний, позитивний | R1 | Так: критичний шлях, стабільні дані |
| TC-AUTH-002 | Вхід з невірним паролем | Як TC-AUTH-001 | 1–3 як у TC-AUTH-001 з невірним паролем | пароль: Wrong#123 | Загальне повідомлення «Невірний email або пароль», без підказки, що саме невірне; сесію не видано | P1 | Негативний, безпека | R3 | Так |
| | | | | | | | | | |

## Розгорнутий формат (для складних кейсів)
```
ID:
Назва: [що перевіряємо] — [за яких умов]
Модуль / вимога:
Пріоритет: P1 | P2 | P3 | P4
Тип: функціональний | негативний | граничний | API | UI | безпека | продуктивність | доступність
Рівень: unit | API | інтеграційний | E2E
Пов'язаний ризик: R…
Передумови:
Тестові дані:
Кроки:
  1.
  2.
Очікуваний результат: (перевірюваний, для кожного важливого кроку)
Постумови / очищення:
Автоматизувати: так | ні — чому
```

## Правила якості
- Один кейс перевіряє одну річ і може впасти лише з однієї причини.
- Очікуваний результат конкретний і перевірюваний («показано помилку X», а не «працює коректно»).
- Дані явні, кейс не залежить від інших кейсів.
- Краще 20 сильних кейсів, що покривають ризики, ніж 200 «для галочки».
